# 视频去重存储方案（OSS 只存一份）

> 需求：用户可能重复提交同一个链接，不同用户也可能提交同一个视频。底层对象存储（OSS/MinIO/COS）对相同视频只保存**一份**。
> 整理日期：2026-11-08

---

## 1. 结论先行

采用 **内容寻址存储（Content-Addressed Storage）+ 引用计数**：

| 项目 | 方案 |
|---|---|
| 去重依据 | 视频文件 **SHA-256**（内容哈希） |
| 对象 key | `media/{sha256前2位}/{sha256}/original.mp4` |
| 元数据 | `media_assets` 表，`sha256` 唯一 |
| 关联 | `projects.media_asset_id` 指向资产，多个项目共享同一资产 |
| 引用计数 | `media_assets.ref_count`，项目创建 +1、删除 -1 |
| 删除 | `ref_count=0` 后延迟 GC，避免并发误删 |
| 链接去重 | 先按平台 ID（抖音 aweme_id、B站 bvid+cid）映射；下载后仍以内容哈希为准 |
| 上传去重 | 服务端边接收边算 SHA-256，命中已有资产则不再上传 |
| 可选增强 | 同一资产的 ASR/分句结果缓存，避免重复转写（省钱） |

> 相同内容不同码率/水印/重新编码，哈希会不同；这类"近似重复"需要平台 ID 或感知哈希，见第 9 节。

### 落地状态（P0）

- ✅ 已实现：`media_assets` / `media_asset_files` / `media_sources` + `projects.media_asset_id`
- ✅ 已实现：上传按 SHA-256 去重；链接按内容哈希 + URL 指纹复用
- ✅ 已实现：原视频 / 720p 代理 / 整段音频按资产共享（一份）
- ✅ 已实现：`ref_count` 引用计数；删除项目减引用；GC 脚本 `python -m src.worker.gc`
- ✅ 已实现：旧项目兼容（`media_asset_id=NULL` 仍走 per-project key）
- ⏳ 待实现：平台 ID 预下载去重（当前用 URL 指纹）、ASR/分句结果缓存、逐句音频按资产共享、感知哈希、存量数据回填

## 2. 现状与问题

当前对象 key 是"按项目"生成的：

```
uploads/{user_id}/{uuid}.mp4                 # 用户上传
projects/{project_id}/source.mp4             # 720p 代理
projects/{project_id}/audio.mp3              # 整段音频
projects/{project_id}/segments/{idx}.mp3     # 逐句音频
```

同一个视频被 N 个用户提交，就会存 N 份原视频、N 份代理、N 份音频，OSS 成本和带宽都被放大。

目标：**原视频只存一份**；代理/音频也可按资产共享。

## 3. 数据模型

### 3.1 资产表

```sql
CREATE TABLE media_assets (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  sha256        CHAR(64)     NOT NULL,
  size_bytes    BIGINT UNSIGNED NOT NULL,
  duration_ms   INT UNSIGNED NULL,
  mime_type     VARCHAR(64)  NULL,
  title         VARCHAR(255) NULL,
  status        VARCHAR(16)  NOT NULL DEFAULT 'active', -- processing/active/blocked/deleted
  ref_count     INT UNSIGNED NOT NULL DEFAULT 0,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  last_used_at  DATETIME     NULL,
  UNIQUE KEY uk_media_assets_sha256 (sha256),
  KEY idx_media_assets_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 3.2 资产文件（多版本）

```sql
CREATE TABLE media_asset_files (
  id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  asset_id    BIGINT UNSIGNED NOT NULL,
  kind        VARCHAR(16) NOT NULL,   -- original / proxy / audio / cover
  object_key  VARCHAR(512) NOT NULL,
  size_bytes  BIGINT UNSIGNED NULL,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_asset_kind (asset_id, kind),
  CONSTRAINT fk_asset_files_asset FOREIGN KEY (asset_id)
    REFERENCES media_assets(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 3.3 来源指纹（减少重复下载）

```sql
CREATE TABLE media_sources (
  id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  fingerprint  VARCHAR(128) NOT NULL,
  asset_id     BIGINT UNSIGNED NOT NULL,
  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_media_sources_fp (fingerprint),
  KEY idx_media_sources_asset (asset_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

指纹示例：

```
douyin:7647447886296304942
bilibili:BV1xx411c7mD:123456
youtube:dQw4w9WgXcQ
upload:sha256:<64位>
url:sha256(<归一化URL>)
```

### 3.4 项目关联

```sql
ALTER TABLE projects ADD COLUMN media_asset_id BIGINT UNSIGNED NULL;
ALTER TABLE projects ADD KEY idx_projects_asset (media_asset_id);
```

- 新项目优先使用 `media_asset_id`。
- `projects.source_video_url` 保留为兼容字段，逐步改为从资产派生。

### 3.5 可选：转写结果缓存

```sql
CREATE TABLE asset_transcripts (
  id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  asset_id     BIGINT UNSIGNED NOT NULL,
  lang         VARCHAR(16) NOT NULL,
  asr_provider VARCHAR(32) NOT NULL,
  asr_version  VARCHAR(32) NOT NULL,
  segments_json MEDIUMTEXT NOT NULL,
  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_asset_transcript (asset_id, lang, asr_provider, asr_version)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

同一资产 + 同语言 + 同 ASR 版本 → 直接复用分句结果，省一次 ASR 费用。

## 4. 对象存储布局

```
media/{sha256[:2]}/{sha256}/
├── original.mp4      # 原始/统一容器
├── proxy.mp4         # 720p H.264/AAC
├── audio.mp3         # 64k 整段音频
└── cover.jpg         # 封面（可选）

projects/{project_id}/segments/{idx}.mp3   # 逐句音频（当前按项目）
recordings/{user_id}/{segment_id}/{uuid}.mp3
```

- `{sha256[:2]}` 只是分片前缀，避免单目录对象过多；MinIO/OSS 都支持。
- 同一资产的所有用户共享 `original/proxy/audio`。
- 逐句音频默认仍按项目存；如果复用 `asset_transcripts`，也可以改为按资产 + 句子索引存。

## 5. 核心流程

### 5.1 用户上传

```
客户端上传文件
   → 服务端边接收边计算 SHA-256（不要信任客户端 hash）
   → 查询 media_assets.sha256
      ├─ 已存在：丢弃临时文件/删除 staging 对象，复用资产，ref_count+1
      └─ 不存在：上传到 media/{sha256[:2]}/{sha256}/original.mp4
                插入 media_assets（唯一索引兜底）
                转码 proxy / 抽 audio（或异步）
   → 创建 project，关联 asset_id，ref_count+1
```

关键点：

- **先判重再上传**：如果服务端能提前拿到 hash（如客户端先算 hash 并上传小文件校验），可省流量；但最终仍由服务端重新计算校验。
- **流式哈希**：用 `hashlib.sha256()` 包裹写入流，避免读两遍。
- **并发同名**：两个请求同时上传同一 hash，唯一索引只会成功一个；另一个捕获 `IntegrityError` 后复用已有资产。对象 key 相同，重复上传也只是覆盖同一对象，仍只有一份。
- **失败清理**：临时对象放 `staging/`，任务失败/超时由 GC 清理。

### 5.2 链接导入

```
解析链接 → 得到平台 ID（如抖音 aweme_id）
   → 查 media_sources.fingerprint
      ├─ 命中且资产可用：跳过下载，直接建项目
      └─ 未命中：下载视频 → 计算 SHA-256 → 查/建资产
   → 写入 media_sources（平台 ID → asset）
   → 创建项目，关联 asset_id
```

- 平台 ID 解析失败时，退回"下载后按内容哈希去重"。
- 不同短链指向同一视频：解析到同一 `aweme_id`/`bvid` 后即可命中。
- 同一视频被不同平台转载（内容重新编码）：内容哈希不同，需感知哈希/人工策略，见第 9 节。

### 5.3 引用计数

创建项目时：

```sql
UPDATE media_assets
SET ref_count = ref_count + 1, last_used_at = NOW()
WHERE id = :asset_id;
```

删除项目/项目过期时：

```sql
UPDATE media_assets
SET ref_count = ref_count - 1
WHERE id = :asset_id AND ref_count > 0;
```

- 必须与项目删除在同一事务。
- 创建项目失败（未关联资产）不要 +1。
- 资产处理失败时，允许 `ref_count=0` 进入 GC。

### 5.4 删除与 GC

不能 `ref_count=0` 立刻删对象：可能刚好有并发请求在引用它。

```
定时任务（如每小时）：
1. 找 status='active' AND ref_count=0 AND last_used_at < now - 24h
2. 再次确认 ref_count 仍为 0
3. 标记 status='deleted'
4. 删除 media_asset_files 对应 OSS 对象
5. 删除资产记录（或保留墓碑记录）
```

- 宽限期可配：`MEDIA_GC_GRACE_SECONDS=86400`。
- 对账任务：定期列出 `media/` 前缀对象，删除无资产引用的孤儿对象。

## 6. 资产与项目的解耦

| 数据 | 归属 | 说明 |
|---|---|---|
| 原视频 / 代理 / 整段音频 | **资产（共享）** | 所有引用项目共享一份 |
| 逐句音频 | 项目（默认） | 可按 `asset_transcripts` 进一步共享 |
| 用户录音 | 用户 | 不变 |
| 标题 / 封面 | 项目或资产 | 标题建议项目级（用户可改），封面可资产级 |
| 转写文本 | 可选资产级缓存 | 同资产同语言复用 |

> 用户修改项目标题不影响资产；不同用户看同一视频可以有不同标题。

## 7. 兼容性与迁移

### 7.1 新代码

- 新增 `media_assets` / `media_asset_files` / `media_sources` 表。
- `projects` 加 `media_asset_id`。
- 上传/链接流程改为"先算 hash / 先查指纹，再决定是否存储"。
- API 返回的视频/音频 URL 从 `media_asset_files` 取，生成 presigned URL。

### 7.2 存量数据

1. 新建表；
2. 遍历现有 `projects`，下载现有对象 → 计算 SHA-256；
3. 相同 hash 只保留一份资产，其他项目改为关联同一 asset；
4. 更新 `projects.media_asset_id`；
5. 可选：删除重复的旧对象（建议先保留 7 天再清理）；
6. 回填 `ref_count`（`SELECT COUNT(*)`）。

> 存量迁移耗时较长，建议写离线脚本、分批执行、可断点续跑。

## 8. 安全与合规

- **哈希不信任客户端**：服务端必须重新计算。
- **内容审核**：同一资产只审一次；命中违规时把 `status='blocked'`，所有引用项目统一不可播放。
- **访问控制**：对象仍是私有读 + 签名 URL；共享对象不等于公开对象。
- **隐私**：不同用户提交相同内容时，系统内部会关联到同一资产，但不要向用户暴露"还有谁提交过"。
- **版权**：去重只减少存储，不改变内容授权；仍要求用户拥有使用权。

## 9. 近似重复（可选增强）

精确 SHA-256 只能去重**完全相同**的文件。以下情况哈希不同：

- 同一视频不同分辨率/码率；
- 带水印 vs 无水印；
- 平台二次转码；
- 重新封装（mp4/mkv）导致字节不同。

可叠加：

1. **平台指纹**（推荐，成本最低）：抖音 `aweme_id`、B站 `bvid+cid`、YouTube `video_id` 作为 `media_sources` 指纹，能覆盖"同一平台同一视频的不同链接"。
2. **流内容哈希**：用 ffmpeg 对音视频流做 hash，忽略容器元数据（比整文件 hash 更稳定）。
3. **感知哈希 / 视频指纹**：pHash、关键帧指纹、音频指纹；成本高，适合大规模内容库去重。
4. **人工/规则**：标题+时长+封面相似度，作为辅助。

建议：P0 用 SHA-256 + 平台指纹；P2 再评估感知哈希。

## 10. 实施计划

### P0（核心去重）
- `media_assets` / `media_asset_files` / `media_sources` 表。
- 上传：流式 SHA-256 → 命中复用，未命中落 `media/...`。

### P2（近似去重）
- 流内容哈希 / 感知哈希。
- 跨平台同一内容识别。

## 11. 测试用例

- 同一文件上传两次 → 1 个 asset、`ref_count=2`、OSS 只有 1 份。
- 两个用户上传同一文件 → 同上。
- 不同文件 → 2 个 asset。
- 并发上传同一文件 → 只创建 1 个 asset，无重复对象。
- 同一抖音短链提交两次 → 命中 `media_sources`，不再下载。
- 抖音短链与完整链接 → 同一 `aweme_id`，命中同一 asset。
- 删除一个项目 → `ref_count` 减 1，对象保留。
- 删除所有引用项目 → 超过宽限期后对象被 GC。
- 资产被标记 blocked → 所有引用项目不可播放。
- 存量迁移后，重复对象清理且项目可正常播放。

## 12. 配置建议

```ini
MEDIA_DEDUP_ENABLED=true
MEDIA_HASH_ALGO=sha256
MEDIA_GC_GRACE_SECONDS=86400

MEDIA_USE_STREAM_HASH=false
```
