# 影子跟读小程序 · 技术方案 v1

> 目标：用户**粘贴链接**或**直接上传本地视频** → 自动提取字幕并切成一句句 → 逐句跟读，原声与自己的录音 A/B 对比。
> 约束：微信小程序首发、安装包小、无发音评分（只做原声 vs 自己录音的听感对比）。
> 内容规模：**视频均 ≤ 5 分钟（短文本）**，上传文件 **≤ 100MB**，单课约 50~150 句，整段一次转写即可。

---

## 0. 决策清单（先看结论）

| 维度 | 决策 | 理由 |
|---|---|---|
| 前端载体 | **uni-app（Vue3 + TypeScript），一套代码发微信小程序 + App** | 后续明确要 App，避免重写；UI 简单，播放/录音两端都有 API；小程序主包仍可 < 1.5MB |
| 端上职责 | 只做 UI、播放、录音；**零模型、零媒体处理** | 主包可控制在 1MB 内，满足"安装包小" |
| 后端 | **Python 3.12 + FastAPI** | ASR/ffmpeg/yt-dlp 生态都在 Python，AI 相关库最全 |
| 异步任务 | **Redis + ARQ（或 Celery）** | 下载 + ASR 是长任务（10s~2min），必须异步化，前端轮询进度 |
| 数据库 | **MySQL 8.0（InnoDB, utf8mb4）** | 课程/句子是强关系数据；生态成熟、云厂商托管实例多；量大后再考虑分表 |
| 对象存储 | 腾讯云 COS + CDN | 音频片段、封面、视频代理直链播放 |
| 内容入口 | **粘贴链接 + 本地视频上传（≤ 5 分钟 / ≤ 100MB）双入口** | 上传路径最合规，且不依赖平台解析，两条路径共用同一处理管线 |
| 视频解析 | **yt-dlp 为主 + 抖音自定义兜底 + 第三方解析 API 兜底** | 单靠一种方案必然随平台改版失效 |
| 字幕 | **平台自带字幕优先，没有则云 ASR（腾讯云录音文件识别）** | 省钱且准；ASR 兜底覆盖 95% 视频 |
| 内容规模 | 单条 ≤ 5 分钟 | 一次整段转写，不需要分片/流式/长音频工程 |
| 切句 | 服务端按"标点 + 停顿 + 时长/字数上限"切分，**预生成单句 mp3 片段** | 跟读要反复听，切片比 seek 延迟低、可循环、可缓存 |
| 播放与全文 | **原视频可播放（链接/上传） + 完整文案全文视图 + 任选一句跟读** | 用户核心诉求：句子列表即全文，任一句可点选下钻 |
| 跟读对比 | **只录音 + A/B 回放，不上传、不评分** | 零成本、零隐私风险、延迟最低 |
| 主体与类目 | **企业主体（已确认）**，类目选"工具-效率"或"教育-在线教育" | 个人主体类目受限，且"视频下载"类功能审核敏感 |

**术语约定**

- **课程（lesson）**：一次链接解析或本地视频上传后生成的**跟读学习单元**，包含标题、封面、时长、句子列表和媒体地址。**它不是视频文件本身。**
- **句子（sentence）**：跟读的最小单位，带原文、起止时间戳、单句音频片段。
- **原视频 / 素材**：用户提供的链接或上传的视频文件，存 COS，7 天后清理；清理后课程和句子仍然可用。

```

│  页面/组件 (UI)                                                    │
│  innerAudioContext / video 播放   |  RecorderManager 录音           │
│  本地文件系统(仅存录音)             |  选视频/压缩 + COS 直传          │
└───────────────┬────────────────────────────┬─────────────────────┘
                │ HTTPS/JSON                 │ 视频直传
┌───────────────▼────────────────────────────▼─────────────────────┐
│                        服务端 (腾讯云)                             │
│      FastAPI 网关 ───────────▶ MySQL 8.0                          │
│           │                                                        │
│           ▼                                                        │
│      Redis 队列 ──▶ Worker (解析/下载/ASR/切句/视频转码)            │
│                          │                                         │
│                          ▼                                         │
│      COS + CDN ◀── 媒体产物    外部服务: yt-dlp/第三方解析 ·        │
│                                腾讯云 ASR · 微信内容安全 ·           │
│                                LLM 纠错/翻译(可选)                  │
└────────────────────────────────────────────────────────────────────┘
```

**分层原则**

1. **重活全在云端**：解析、下载、上传校验、转码、ASR、切句都在 Worker 做，小程序只拿"成品"（句子列表 + 音频 URL）。
2. **端上录音不出端**：录音文件只存小程序本地，服务端不感知，既省存储又规避隐私与审核问题。
3. **长任务异步化**：创建课程立即返回 `lessonId`，前端 2~3 秒轮询一次状态，避免小程序 10s 请求超时。
4. **上传走 COS 直传**：视频不经过自己的 API 服务器，避免请求体限制和带宽瓶颈；服务端只发临时凭证、做二次校验。

## 3. 关键技术方案

### 3.1 链接解析（最大的不确定性来源）

输入是"分享文案"而不是干净 URL，第一步必须先清洗：

```python
# 抖音分享文案示例：
# "7.43 复制打开抖音，看看【xxx】的作品 https://v.douyin.com/iRNBho6u/ ..."
URL_RE = re.compile(r"https?://[^\s，。！？、（）()【】]+")
url = URL_RE.search(share_text).group(0)
```

| 平台 | 方案 | 成功率 | 备注 |
|---|---|---|---|
| 抖音 | 短链 302 → 取 `item_id`；移动端 UA 请求页面，从 `window._ROUTER_DATA` 取 `video.play_addr.url_list`；`playwm` 域名替换为 `play` 去水印 | 高 | 页面结构会变，需监控 + 兜底 |
| B站 | yt-dlp 原生支持；或 `x/web-interface/view` 拿 cid 后请求字幕接口 | 高 | 部分视频有 CC 字幕，优先用 |
| YouTube | yt-dlp；字幕走 `timedtext` | 高 | 需海外出口，国内访问受限 |
| 小红书 / 快手 | yt-dlp 或第三方解析 API | 中 | 按需接 |
| 微信视频号 | **MVP 不支持** | 低 | 需要登录态 + 签名 + 解密，且在小程序内解析微信自家内容审核风险极高 |
| 本地视频上传 | `wx.chooseMedia` → COS 直传 | 高 | **核心入口之一**（与链接并列）；不依赖平台解析，合规性最好，详见 3.2.1 |

**为什么视频号链接和普通视频链接不是一回事？**

普通视频链接（抖音/B站/YouTube）本质是**公开网页**：服务端用普通 HTTP 请求就能拿到页面或 API，再从里面提取媒体地址。视频号是**微信登录态下的私有内容**，差异在：

1. **不是公开页面**：视频号链接在浏览器里打开会提示"请在微信客户端打开"，服务端没有微信登录态，拿不到内容。
2. **强鉴权 + 动态签名**：播放依赖 `uin`、`session`、`ticket` 等登录凭证和设备指纹，签名参数动态生成。
3. **媒体地址短时效**：`finder.video.qq.com` 的地址带加密参数，几分钟到几十分钟就失效，且请求需要特定 Referer/Cookie。
4. **分享形态不同**：视频号分享出去是卡片/小程序跳转，很多场景用户根本拿不到一条可复制的 URL。
5. **反爬与合规**：腾讯对视频号抓取风控很严；在微信小程序里绕过微信自家机制，审核和封号风险都极高。

所以首版不做视频号；用户可以通过**本地视频上传**（相册里保存/录屏的视频）继续使用，走同一条 ASR 链路。

> **合规提示**：只做"用户提供、用户有权使用的内容"的学习工具；不提供批量下载、不破解付费内容、不提供去水印导出。页面上要有免责声明与侵权投诉入口。

**为什么用 yt-dlp，而不是自己写解析？**

- 支持上千个站点，抖音/B站/YouTube/TikTok 等主流平台开箱即用；短链跳转、签名、UA/Cookie、m3u8 合并、格式选择都由它处理。
- 平台改版是常态，yt-dlp 社区跟进快；自己维护每个平台的解析器，等于持续养一个反爬团队。
- 服务端运行、开源免费（Unlicense），不增加小程序包体。
- 它不是银弹：抖音部分链接仍可能需要 Cookie/自定义兜底，所以方案保留"yt-dlp + 自定义解析 + 第三方 API"三层。若产品改成纯本地上传，可直接去掉。

### 3.2 下载与音频抽取

```bash
# 下载（限制时长/体积，防滥用）
yt-dlp --no-playlist --max-filesize 200M -f "bestaudio/best" -o "/data/{id}.%(ext)s" "$URL"

# 统一转 16k 单声道 PCM，喂给 ASR
ffmpeg -y -i input.mp4 -vn -ac 1 -ar 16000 -acodec pcm_s16le -f wav output.wav
```

- Worker 沙箱目录按 `taskId` 隔离，任务结束即清理；原始视频默认保留 7 天用于视频模式，之后删除，只留音频与句子。
- 链接下载限制：单条 ≤ 5 分钟、≤ 200MB、并发 per user ≤ 1，防止被当成免费下载器刷。超过 5 分钟直接拒绝，提示"目前仅支持 5 分钟以内的视频"；用户上传路径另有 **100MB 硬上限**（见 3.2.1）。

### 3.2.1 本地上传链路（与链接路径并列）

**客户端**

- 入口：首页"上传视频"，`wx.chooseMedia({ count: 1, mediaType: ['video'], sourceType: ['album', 'camera'] })`。注意 `maxDuration` 只限制小程序内拍摄（最长 60s），**相册选择不受限**，5 分钟视频从相册选即可。
- 选中后先校验 `tempFiles[0].duration ≤ 300s`、`size ≤ 100MB`（硬上限）。超过 100MB 先压缩；压缩后仍超 100MB 则拒绝，提示换更短或更低清晰度的视频。
- 体积大时先压缩：用 `wx.compressVideo` 压到 720p 左右、码率约 1Mbps（5 分钟约 35~40MB），再上传；展示压缩与上传进度。
- 直传 COS：先调 `POST /v1/uploads` 拿 STS 临时密钥/预签名 URL，再用 COS 小程序 SDK（或分片上传）直传，对象 key 为 `uploads/{userId}/{uuid}.mp4`；支持进度、暂停/续传。
- 上传完成后调 `POST /v1/uploads/{lessonId}/complete`，进入处理队列。

**服务端**

- 发凭证时校验登录态、文件大小/类型/时长（客户端传入值仅作预检）。
- 收到 complete 后 `HEAD` 对象 + `ffprobe` 二次校验：对象 ≤ 100MB、时长 ≤ 300s、容器/编码在白名单、**必须存在音轨**（无音轨报 `NO_AUDIO`），否则拒绝并删除对象。
- 校验通过后与链接路径汇合：抽 16k wav → ASR → 切句 → 切片 → 生成 720p 代理。
- 原始上传视频保留 7 天，之后删除，只留音频与句子；未完成上传的 `awaiting_upload` 课程 24 小时后清理。

**与链接路径的关系**

- `lessons.source_type` 区分 `link / upload`；Worker 的"取媒体"步骤不同，后续转写、切句、播放完全复用。
- 上传路径没有平台字幕，**一律走 ASR**。
- 合规上最稳：内容是用户自己上传的，审核说明也更清晰。

**App 端**

- 用 `uni.chooseVideo`，其余流程一致；App 可直接读本地文件，支持更大文件与后台上传（M4）。

### 3.3 字幕获取（优先平台字幕，ASR 兜底）

**优先级**：平台 CC 字幕 → 云 ASR → 用户手动粘贴字幕（P1）。

| ASR 方案 | 中英混合 | 时间戳 | 成本 | 结论 |
|---|---|---|---|---|
| 腾讯云录音文件识别 | 好 | 句级 | 约 1~3 元/小时音频 | **MVP 首选**（与 COS/服务器同云，内网传输快） |
| 阿里云录音文件识别 | 好 | 句级 | 类似 | 备选，接口可插拔 |
| 讯飞 | 好 | 句级 | 类似 | 备选 |
| 自建 FunASR（Paraformer + VAD + 标点） | 好 | 词级 | 仅服务器成本 | 量起来后降本首选，需 GPU 或接受 CPU 慢 |
| faster-whisper | 英文更强 | 词级 | 服务器成本 | 英文场景备选，长音频需 GPU |

**为什么是腾讯云 ASR？**

- 与 COS、服务器同属腾讯云：内网传输、同一账号计费、同一区域合规，少一套跨云配置。
- 5 分钟内音频一次异步请求即可，返回句级时间戳和标点，正好是切句需要的格式。
- 不需要 GPU 和模型运维，MVP 上线最快；按音频时长付费，5 分钟约 ¥0.1~0.25。
- **不是锁定**：后端封装 `Transcriber` 接口，阿里云/讯飞/自建 FunASR 均可替换；量起来后自建 FunASR 降本。
- 注意：中英混合的实际准确率必须用真实视频做 A/B，不同模型/套餐差异较大；平台 CC 字幕可用时优先用字幕，ASR 只是兜底。

**关键点**

- ASR 直接返回**句级时间戳**最好；只有词级时间戳时，按标点 + 停顿做二次对齐。
- ASR 结果建议再过一遍 LLM 做**纠错 + 补标点**（不改时间戳），中英混读的专有名词准确率提升明显；提示词要求"只输出校正后的文本，不增删句子"。
- 可选：用 LLM 生成中文/英文**参考译文**（跟读页可折叠展示，P1）。

### 3.4 切句算法

目标：每句 1.5s ~ 15s、≤ 60 字符，语义完整，便于跟读。

```python
def segment(sentences):
    # 1) ASR 原始句级结果
    # 2) 若单句 > 15s 或 > 60 字，按逗号/停顿 > 400ms 再切
    # 3) 若单句 < 1.5s 或 < 6 字，与相邻句合并
    # 4) 保留 start_ms / end_ms，句间不重叠
    ...
```

- 标点优先（。！？!?；…），其次长停顿（VAD 结果或相邻词时间差 > 400ms）。
- 句子前后各留 100~200ms 余量，避免首尾音被切掉。
- 输出结构：

```json
{ "id": "s_12", "idx": 12, "text": "I've been learning English for three years.",
  "startMs": 42300, "endMs": 47100, "audioUrl": "https://cdn/.../s_12.mp3" }
```

### 3.5 媒体生成

```bash
# 单句片段：32kbps 单声道 mp3，10s 约 40KB，100 句约 4MB/课
ffmpeg -y -i full.wav -ss 42.3 -to 47.1 -ac 1 -b:a 32k s_12.mp3

# 视频模式：不切视频，前端用原视频/720p 代理 seek
ffmpeg -y -i input.mp4 -vf scale=-2:720 -c:v libx264 -crf 28 -c:a aac -b:a 64k proxy.mp4
```

- **音频按句预切**：跟读是高频重复播放，切片无 seek 延迟，且能走 CDN 缓存、支持单句循环。
- **视频不预切**：切太多文件不划算，前端 `video` 组件 `seek(startMs)` → `timeupdate` 到 `endMs` 暂停即可；给 720p 代理降低流量。
- 句子多时 Worker 内并行 ffmpeg（按 CPU 数限并发）。

### 3.6 播放

- 单句原声：`wx.createInnerAudioContext()`，`src` 为 CDN 片段；支持 `loop`、`playbackRate`（0.75/1.0/1.25 倍速）、`seek`。
- 视频模式：`<video>` 组件 + `initial-time`，监听 `bindtimeupdate`，超过 `endMs` 即暂停。
- 体验优化：进入跟读页时预加载当前句 + 下一句音频；切句时复用同一个音频实例，只换 `src`。

### 3.7 录音与 A/B 对比（无评分）

```js
// 录音：mp3，44.1k（兼容性最好），最长 60s，够覆盖单句
const rec = wx.getRecorderManager()
rec.start({ duration: 60000, format: 'mp3', sampleRate: 44100, numberOfChannels: 1 })
rec.onStop(({ tempFilePath, duration }) => {
  const dest = `${wx.env.USER_DATA_PATH}/rec/${lessonId}_${sentenceId}.mp3`
  wx.getFileSystemManager().copyFileSync(tempFilePath, dest)
  // 元数据存 Storage：{ sentenceId, path, duration }
})
```

- 录音存本地，删除课程时一并清理；**不上传服务端**。

### 3.8 数据模型

```sql
-- MySQL 8.0，utf8mb4，InnoDB
-- 用户
create table users (
  id bigint unsigned primary key auto_increment,
  openid varchar(64) not null,
  created_at datetime(3) not null default current_timestamp(3),
  unique key uk_openid (openid)
) engine=InnoDB default charset=utf8mb4;

-- 课程：一次链接解析或本地上传生成的跟读学习单元（不是视频文件本身）
create table lessons (
  id bigint unsigned primary key auto_increment,
  user_id bigint unsigned not null,
  source_type varchar(16) not null default 'link',  -- link / upload
  source_url text null,                             -- 上传时为空
  origin_object_key varchar(255) null,              -- 上传视频在 COS 的 key
  file_size bigint unsigned null,
  platform varchar(24) not null,                    -- douyin / bilibili / youtube / upload
  title varchar(255),
  cover_url varchar(1024),
  duration_ms int unsigned,
  audio_url varchar(1024),                          -- 整段音频（可选）
  video_url varchar(1024),                          -- 原视频/720p 代理
  status varchar(16) not null,                      -- awaiting_upload/queued/.../ready/failed
  error_code varchar(32),
  created_at datetime(3) not null default current_timestamp(3),
  expire_at datetime(3),                            -- 原始视频清理时间
  key idx_user_created (user_id, created_at),
  constraint fk_lessons_user foreign key (user_id) references users(id)
) engine=InnoDB default charset=utf8mb4;

-- 句子
create table sentences (
  id bigint unsigned primary key auto_increment,
  lesson_id bigint unsigned not null,
  idx int not null,
  text text not null,
  translation text,
  start_ms int unsigned not null,
  end_ms int unsigned not null,
  audio_url varchar(1024),
  unique key uk_lesson_idx (lesson_id, idx),
  constraint fk_sentences_lesson foreign key (lesson_id) references lessons(id) on delete cascade
) engine=InnoDB default charset=utf8mb4;

-- 用户录音只存本地，服务端不建表
```

**为什么需要数据库，而不是 JSON 文件或 Redis？**

- 数据是强关系的：用户 → 课程 → 句子，需要按 `user_id` 列课程、按 `lesson_id` 取有序句子、删课程级联删句子。
- 需要事务：创建课程和写入几十上百句必须原子完成；Worker 改状态要避免并发覆盖。
- 需要索引与查询：课程列表、状态轮询、每日配额统计，靠文件遍历或 Redis key 都不划算。
- Redis 是队列/缓存，不承担持久化真相；进程重启、内存淘汰都可能丢数据。
- SQLite 也够早期单机跑，但多 Worker 并发写会锁；MySQL 托管实例运维省事、扩容路径清晰。

### 3.9 接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/lessons` | 链接入口：body `{url}` → `{lessonId, status}`；校验 URL 域名白名单 |
| GET | `/v1/lessons/{id}` | 返回状态、进度、元信息；ready 时带 `sentences[]` |
| GET | `/v1/lessons?cursor=` | 我的课程列表 |
| DELETE | `/v1/lessons/{id}` | 删除课程与 COS 资源 |
| POST | `/v1/uploads` | 上传入口：body `{fileName,size,durationMs}` → `{lessonId, objectKey, credentials, expiresAt}`，课程状态 `awaiting_upload` |
| POST | `/v1/uploads/{lessonId}/complete` | 直传完成后回调；服务端 HEAD + ffprobe 校验（≤5min、有音轨）后入队 |
| GET | `/v1/health` | 健康检查 |

- 鉴权：`wx.login` → `code2session` → 自签 JWT，请求头 `Authorization: Bearer`。
- 轮询：前端每 2~3s 拉一次详情，`ready/failed` 停止；P1 可换 WebSocket。
- 媒体直链：COS 私有读 + CDN 鉴权；小程序后台把 CDN 域名加入 **downloadFile / 媒体域名**白名单（必须已备案 + HTTPS）。

### 3.10 任务状态机

```
链接：queued → resolving → downloading → transcribing → segmenting → ready
上传：awaiting_upload → validating → transcribing → segmenting → ready
                                  ↘ failed（error_code 可展示可重试）
```

每个阶段回写 `progress` 与 `stage`。前端展示：链接路径"解析链接 → 下载中 → 提取字幕 → 切分句子"，上传路径"上传中 → 校验中 → 提取字幕 → 切分句子"。

**为什么需要 Redis？**

- **异步任务队列**：下载、ASR、切片是 10~90 秒的长任务，不能塞进 HTTP 请求；API 只负责入队，Worker 消费。ARQ 基于 Redis 提供入队、重试、延迟任务。
- **进度缓存**：小程序每 2 秒轮询，API 先读 Redis 里的 `progress/stage`，避免高频查询打 MySQL；任务完成后再回写数据库。
- **限流与配额**：`INCR + EXPIRE` 原子计数，按 openid 限制每日课程数和并发，比数据库行锁轻。
- **幂等/去重锁**：`SET NX EX` 防止同一课程重复入队、并发重复处理。
- 可选：P1 的 WebSocket 进度广播、热点课程短期缓存。

**它不是必须的**：低流量 MVP 也可以用 MySQL 任务表（`SELECT ... FOR UPDATE SKIP LOCKED`）+ 轮询实现队列，少一个组件。但 Redis 一个容器/托管实例很便宜，能同时解决队列、限流、缓存三件事，所以默认保留；如果去掉，就要自己实现重试、延迟、并发控制和过期清理。

**注意**：Redis 不是真相来源。任务状态以 MySQL 为准，开启 AOF；任务设计成幂等，再加一个定时巡检（`processing` 超过 N 分钟就重新入队），防止 Redis 丢数据导致课程卡死。

### 3.11 短视频（≤ 5 分钟）带来的简化

单条内容 ≤ 5 分钟，砍掉了大量长音频工程复杂度：

- **一次整段转写**：不需要按静音切块、不需要分段拼接时间戳；5 分钟 16k 单声道 wav 约 9.6MB，一次 ASR 请求即可。
- **全文 LLM 纠错**：整篇约 600~1200 词，一次提示词完成纠错 + 补标点（可选翻译），上下文很小，成本可忽略。
- **延迟目标**：下载 5~15s + ASR 10~30s + 切片 5~15s，端到端 **P50 < 40s，P90 < 90s**；状态页 + 2s 轮询足够，不必上 WebSocket。
- **并发模型**：ASR 是外部 API 等待，不占 CPU；主要压力是 ffmpeg 切片，2C4G 单机同时处理 2~3 个任务即可，超出则排队。
- **存储量级**：单课句子音频约 1.2MB（32kbps × 5 分钟），1000 课约 1.2GB，COS 成本几元/月；原始视频 7 天清理。
- **仍保留异步任务**：不是为了长任务，而是避开小程序请求超时（>10s）和用户切后台；同步接口只适合 <10s 的纯查询。
- **可选优化（P2）**：ASR 完成后先回传前 20 句，用户立即开始跟读，剩余句子后台继续切——短视频场景收益有限，优先级低。

### 4.2 包体控制（"安装包不能太大"的落地）

|---|---|

## 6. 安全与合规（重点，决定能不能上线）

1. **审核风险**：小程序对"下载他人平台视频"敏感。定位必须是**语言学习工具**，文案避免"下载/去水印/破解"；主按钮叫"生成跟读课程"而非"下载视频"。链接解析与本地视频上传是**并列主入口**，审核材料里强调上传路径。
2. **本地上传是主入口，不是隐藏兜底**：`wx.chooseMedia` 从相册选择自己的视频，走同一条 ASR 链路；解析失败或审核受限时，产品仍然完整可用。
3. **内容安全**：课程标题、ASR 文本、封面过微信 `msgSecCheck` / `mediaCheckAsync`，命中即拒绝；上传视频的封面与转写文本同样要检查。
4. **SSRF 防护**：解析 URL 只允许 http/https + 域名白名单，解析出的媒体地址禁止内网 IP；下载设超时与体积上限。
5. **上传安全**：COS 临时凭证按 `uploads/{userId}/` 前缀授权、15 分钟过期、限制 Content-Type 与 **100MB 上限**（policy 的 `content-length-range`）；`complete` 时服务端二次校验，禁止拿别人的 objectKey 建课。
6. **限流与防滥用**：按 openid 限每日课程数（如 20 条）、并发 1；上传同样计入配额；识别异常高频调用。
7. **版权**：首次使用勾选"我拥有该内容的使用权，仅用于个人学习"；提供侵权投诉入口；原始视频 7 天自动清理。
8. **隐私**：录音仅存本机，隐私政策需明确说明；上传视频仅用于本次转写与跟读，不用于训练或对外展示。

## 10. App 有必要吗：go/no-go 评估

**结论：App 不是"有了小程序就该做"，而是由验证结果触发。** 小程序负责获客、试用、分享；App 负责留存、习惯、离线、推送和支付。两者不是替代关系，是不同阶段的产品形态。

### 10.1 什么情况下没必要做 App

- 用户以"一次性工具"为主：粘链接、跟读一遍就走，周使用 < 2 次。
- 没有订阅/付费计划，或付费意愿未验证。
- 团队小，维护两个发布渠道（小程序审核 + iOS 审核 + 双端兼容）会拖慢迭代。
- 用户没有明确提出离线、后台播放、通知提醒的需求。

### 10.2 什么情况下值得做 App

| 信号 | 建议阈值（可调） | 说明 |
|---|---|---|
| 留存 | 7 日留存 ≥ 25%，周均使用 ≥ 3 次 | 说明是习惯型产品，值得用 App 承接 |
| 使用深度 | 人均单次 ≥ 15 分钟 | 短视频场景下说明用户真的在练 |
| 场景诉求 | ≥ 20% 活跃用户反馈要离线/后台/推送 | 小程序的天花板开始出现 |
| 变现 | 准备做订阅，尤其 iOS 端 | 小程序 iOS 虚拟支付受限，App 内购更可控 |
| 技术 | 小程序边播边录体验不达标（重点验证项） | 影子跟读的核心交互，原生音频会话控制更稳 |
| 规模 | DAU ≥ 3,000~5,000 | 才摊得平双端维护成本 |

> 建议上线后观察 **8 周**：以上信号命中 2 项以上再启动 App；一项都不命中，就把资源投到解析成功率、ASR 质量、内容运营上。

### 10.3 两端分工（如果做 App）

| 能力 | 小程序 | App |
|---|---|---|
| 链接 / 上传生成课程 | ✅ 主入口 | ✅ |
| 单句跟读 + A/B 对比 | ✅ | ✅ 更稳的音频会话 |
| 离线课程包 | ⚠️ 本地缓存有限 | ✅ |
| 后台/锁屏播放 | ⚠️ 受限 | ✅ |
| 每日练习推送 | ⚠️ 订阅消息触达弱 | ✅ |
| 订阅付费 | ⚠️ iOS 受限 | ✅ 内购 |
| 社交分享获客 | ✅ 强 | ❌ 弱 |

### 10.4 技术前置：M1 就要验证"边播边录"

"影子跟读"要求原声播放和用户录音同时进行。小程序在 iOS 上的音频会话控制不如原生稳定（可能被系统打断、音量闪避），这是**决定 App 优先级的关键技术点**。M1 必须在 iOS/Android 真机上实测：

- 播放原句的同时开始录音，录音里是否只有人声、没有原声回授；
- 录音过程中原声是否被暂停或音量骤降；
- 连续跟读 10 句后是否出现音频通道异常。

如果体验不达标，App 的启动时间应提前，而不是等留存数据。
