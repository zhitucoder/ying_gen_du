# 昵称唯一命名方案

> 需求：默认昵称从 `学神01` 开始，支持 `学神{数字}`、`学霸{数字}` 等前缀，未来可扩展；**昵称全局唯一**；用户可以修改昵称。
> 整理日期：2026-11-08

---

## 1. 结论先行

| 项目 | 方案 |
|---|---|
| 默认格式 | `前缀 + 两位补零序号`，如 `学神01`、`学神02`、`学霸01` |
| 前缀 | 可配置，默认 `学神`；预留 `学霸`，未来加前缀只改配置/表 |
| 序号 | **按前缀各自从 01 开始**（学神01 与 学霸01 是不同昵称） |
| 唯一性 | `users.nickname` 加**唯一索引**，并在应用层做冲突处理 |
| 并发安全 | 独立序列表 + `INSERT ... ON DUPLICATE KEY UPDATE ... LAST_INSERT_ID()` 原子取号 |
| 用户修改 | `PATCH /api/auth/me` 修改昵称，校验格式 + 唯一性 |
| 生成冲突 | 若生成的名字已被用户手动占用，自动跳号重试 |

> 如果希望所有前缀共用一个号码池（学神01、学霸02、学神03…），把序号表从"按前缀"改成"单行全局"即可；下方默认按前缀独立。

### 落地状态（当前代码）

- ✅ 已实现：`nickname_counters` 原子取号、`users.nickname` 唯一索引
- ✅ 已实现：注册默认生成 `学神NN`，支持 `nickname_prefix=学霸`
- ✅ 已实现：`PATCH /api/auth/me` 修改昵称（唯一性/长度/全角归一化）
- ✅ 已实现：启动时清理空昵称与重复昵称，再建唯一索引
- ⏳ 待扩展：敏感词审核、昵称修改频率限制

## 2. 命名规则

### 2.1 格式

```
昵称 = 前缀 + 序号
序号 = 至少两位，不足补 0；超过 99 自然进位
```

示例：

```
学神01
学神02
...
学神99
学神100
学霸01
学霸02
```

### 2.2 前缀

- 默认前缀：`学神`
- 已预留：`学霸`
- 未来扩展：`学魔`、`学仙` 等，只需加入前缀配置/表，不改代码逻辑。

建议配置：

```ini
NICKNAME_DEFAULT_PREFIX=学神
NICKNAME_ALLOWED_PREFIXES=学神,学霸
NICKNAME_SEQUENCE_WIDTH=2
```

前缀来源二选一：

1. **后端默认**：不传就用 `学神`；
2. **用户选择**：注册时可传 `nickname_prefix=学霸`（必须在允许列表内）。

### 2.3 唯一性与字符规范

- `nickname` **全局唯一**（MySQL `utf8mb4_unicode_ci`，大小写不敏感）。
- 修改/注册时统一处理：
  - 去首尾空格；
  - Unicode `NFKC` 归一化（全角数字 `０１` → `01`）；
  - 去除零宽字符；
  - 长度 2–20 个字符（数据库列可保留 64，应用层限制 20）；
  - 禁止控制字符、换行。
- 空昵称不允许；不合法直接 400。
- 建议对昵称做敏感词/内容审核（可复用微信 `msgSecCheck` 或自有词库）。

## 3. 数据模型

### 3.1 users 表

```sql
ALTER TABLE users ADD UNIQUE KEY uk_users_nickname (nickname);
```

> 现有库可能有重复/空昵称，必须先清洗再加唯一索引，见第 6 节迁移。

### 3.2 序列表

```sql
CREATE TABLE nickname_counters (
  prefix      VARCHAR(16) NOT NULL PRIMARY KEY,
  next_value  BIGINT UNSIGNED NOT NULL DEFAULT 0,
  updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- 每个前缀一行。
- 初始化：

```sql
INSERT IGNORE INTO nickname_counters(prefix, next_value) VALUES
  ('学神', 0), ('学霸', 0);
```

### 3.3 为什么不用 `users.id` 直接拼昵称

- 现有用户 id 已从 8 开始，直接拼会出现 `学神08` 起步；
- 多个前缀需要各自计数；
- 用户手动改名会占用未来号码，必须能跳号；
- 独立序列表可持久化、可重置、可审计，且与 Redis 无关。

## 4. 生成算法（并发安全）

### 4.1 原子取号（MySQL）

```sql
INSERT INTO nickname_counters(prefix, next_value)
VALUES (:prefix, 1)
ON DUPLICATE KEY UPDATE
  next_value = LAST_INSERT_ID(next_value + 1);

SELECT LAST_INSERT_ID();
```

- 第一次插入时 `LAST_INSERT_ID()` 可能未设置，可在插入后统一 `SELECT next_value`；
- 更稳妥的写法（事务内）：

```sql
INSERT IGNORE INTO nickname_counters(prefix, next_value) VALUES (:prefix, 0);
SELECT next_value FROM nickname_counters WHERE prefix = :prefix FOR UPDATE;
UPDATE nickname_counters SET next_value = next_value + 1 WHERE prefix = :prefix;
```

### 4.2 生成流程

```
1. 校验前缀在允许列表
2. 取号 n
3. 生成 "前缀 + 补零(n)"，如 学神(n)
4. 查 users.nickname 是否已存在
   - 不存在：使用
   - 已存在（被手动占用）：回到第 2 步继续取号
5. 插入用户；若唯一索引冲突（并发）：
   - 重新取号重试（最多 5 次）
   - 仍失败：返回 500 或让用户稍后重试
```

伪代码：

```python
def next_nickname(db, prefix: str) -> str:
    for _ in range(5):
        value = increment_counter(db, prefix)          # 原子自增
        nickname = f"{prefix}{value:0{width}d}"
        if not db.scalar(select(User).where(User.nickname == nickname)):
            return nickname
    raise RuntimeError("nickname allocation failed")
```

### 4.3 并发与唯一索引

- 取号原子，不会出现两个请求拿到同一号码；
- 即使发生唯一索引冲突（例如手工占用），捕获 `IntegrityError` 后重新取号；
- **不要**先查再插（存在竞态），最终以唯一索引为准。

## 5. 用户修改昵称

### 5.1 接口

```http
PATCH /api/auth/me
Authorization: Bearer <token>
Content-Type: application/json

{ "nickname": "学神小明" }
```

响应：`UserOut`（含 `nickname`）。

错误：

| HTTP | detail |
|---|---|
| 400 | 昵称长度/字符不合法 |
| 409 | 昵称已被使用 |
| 401 | 未登录 |

### 5.2 后端逻辑

```python
nickname = normalize_nickname(body.nickname)
if not nickname:
    raise HTTPException(400, "昵称不能为空")
existing = db.scalar(select(User).where(User.nickname == nickname, User.id != user.id))
if existing:
    raise HTTPException(409, "昵称已被使用")
user.nickname = nickname
try:
    db.commit()
except IntegrityError:
    db.rollback()
    raise HTTPException(409, "昵称已被使用")
```

### 5.3 前端

- 首页用户栏显示昵称，旁边加"修改昵称"。
- 弹窗输入 → 保存 → 更新本地 `yg_user` 缓存。
- 收到 409 提示"昵称已被占用"，不关闭弹窗。

## 6. 存量用户迁移

现有用户昵称来源：`alice`、`手机用户`、`139****0001`、`dev` 等，可能重复或为空。

迁移步骤（一次性脚本 `scripts/migrate_nickname_unique.py`）：

1. 创建 `nickname_counters`，初始化前缀。
2. 找出 `nickname IS NULL OR nickname=''` 的用户，按 `id ASC` 生成默认昵称。
3. 找出重复昵称（大小写/全半角归一化后相同）：
   - 保留最早注册的一个；
   - 其余按默认规则重新生成。
4. 校验所有昵称满足长度/字符规则；不满足的重新生成。
5. 加唯一索引 `uk_users_nickname`。
6. 记录迁移日志（user_id、旧昵称、新昵称）。

> 迁移前先备份 `users` 表；脚本需可重复执行（幂等）。

## 7. 注册流程变更

| 场景 | 当前 | 新方案 |
|---|---|---|
| 用户名注册 | 默认昵称 = username | 默认 `学神NN` |
| 手机号注册 | 默认昵称 = 手机号脱敏 | 默认 `学神NN` |
| 用户填写昵称 | 直接保存 | 校验 + 唯一性检查 |
| 可选前缀 | 无 | 注册可传 `nickname_prefix`（学神/学霸） |

- 客户端不传 `nickname` → 后端生成默认昵称。
- 客户端传 `nickname` → 校验后使用；冲突返回 409。
- 注册响应返回最终昵称。

## 8. 扩展性

- **新增前缀**：往 `NICKNAME_ALLOWED_PREFIXES` 和 `nickname_counters` 加一行即可。
- **号码池模式**：
  - 当前：每个前缀独立序号（学神01、学霸01）。
  - 如需全局序号：序列表只保留一行 `default`，生成时统一取号，前缀只影响展示。
- **自定义模板**：未来可扩展为 `前缀 + 序号 + 后缀`，序列表结构不变。
- **回收号码**：不建议复用已注销用户的号码，避免历史混淆；如需回收，增加 `released_numbers` 表。

## 9. 测试用例

- 连续注册 3 个用户 → `学神01`、`学神02`、`学神03`。
- 注册时选择 `学霸` → `学霸01`。
- 并发 100 个注册 → 昵称无重复、无空洞（允许因冲突跳号）。
- 手动把昵称改成 `学神05`，之后生成到 05 时自动跳到 06。
- 修改昵称为已存在昵称 → 409。
- 修改昵称为非法字符/超长 → 400。
- 全角数字 `学神０１` 归一化为 `学神01`，判重生效。
- 存量重复昵称迁移后全部唯一。
