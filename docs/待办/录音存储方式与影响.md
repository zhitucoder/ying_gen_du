## 1. 当前实现（事实）

### 1.1 存储位置

用户录音最终存在 **MinIO 对象存储**，不是本地磁盘。

对象 key：

```
recordings/{user_id}/{segment_id}/{uuid}.mp3     # 微信小程序 / App
recordings/{user_id}/{segment_id}/{uuid}.webm    # H5 MediaRecorder
```

- 本地只写临时文件到 `settings.work_dir/recordings/`（默认 `/tmp/yinggen/recordings`），上传成功后立即删除。
- 每次上传生成新的 `uuid`，所以对象 key 不同。

### 1.2 数据库表

```sql
CREATE TABLE recordings (
  id                BIGINT NOT NULL AUTO_INCREMENT,
  segment_id        BIGINT NOT NULL,
  user_id           BIGINT NOT NULL,
  audio_url         VARCHAR(1024) NOT NULL,  -- 对象 key，不是 URL
  duration_ms       INT DEFAULT NULL,
  score             INT DEFAULT NULL,        -- 预留，未使用
  score_detail_json TEXT,
  created_at        DATETIME NOT NULL DEFAULT now(),
  PRIMARY KEY (id),
  KEY idx_recordings_segment_user (segment_id, user_id),
  CONSTRAINT fk_recordings_segment FOREIGN KEY (segment_id)
    REFERENCES segments(id) ON DELETE CASCADE,
  CONSTRAINT fk_recordings_user FOREIGN KEY (user_id)
    REFERENCES users(id) ON DELETE CASCADE
);
```

### 1.3 写入逻辑

`POST /api/segments/{segment_id}/recordings`：

1. 校验 segment 属于当前用户；
2. 接收 multipart 文件，写本地临时文件；
3. 上传到 MinIO，key 为 `recordings/{user_id}/{segment_id}/{uuid}{ext}`；
4. `INSERT` 一条 `recordings` 记录；
5. 返回 `RecordingOut`，`audio_url` 是 presigned URL。

### 1.4 查询/返回

- 目前只有 `GET /api/recordings/{id}`（按 id 查单条）。
- **没有** `GET /api/segments/{id}/recordings`（按句列出所有录音）。
- 前端跟读页只保存**最后一次上传接口的返回 URL**，用于播放和 A/B。

### 1.5 新旧判断

- 数据库没有 `is_latest` / `version` / `take_no` 字段。
- 新旧靠 **`id`** 判断：`ORDER BY id DESC LIMIT 1` 是最新一条。
- `created_at` 只有**秒级精度**，同一秒内多次录音时间相同，不能单独用于排序。
- 同一句重复录音会**新增一行**，没有 `(segment_id, user_id)` 唯一约束。

### 1.6 删除

- `DELETE /api/projects/{id}`：删除项目时收集该项目的录音对象 key，删除 MinIO 对象；DB 记录由外键级联删除。
- 删除 segment 时，`recordings` 通过 `ON DELETE CASCADE` 删除。
- 没有“删除单条录音”的接口。

### 1.7 前端行为

`src/miniapp/src/pages/shadow/shadow.vue`：

- 点“录音 → 停止”后上传，拿到 `audio_url` 赋给 `recordingUrl`；
- 再次录音会覆盖 `recordingUrl` 变量（只影响 UI）；
- 切换句子 `go()` 会清空 `recordingUrl`；
- 页面刷新后不会拉取历史录音，所以历史录音**不可见**。

---

## 2. 关键结论

1. **录音是 append-only**：每次录音都新增一条 DB 记录 + 一个 MinIO 对象，旧录音不会自动删除或覆盖。
2. **数据库不标记“最新”**：最新 = 最大 `id`；`created_at` 只有秒级精度。
3. **前端只展示最新一次**：后端保留全部，但 UI 没有历史入口。
4. **没有按句查询录音列表的接口**：历史录音无法在 UI 中找回。
5. **删除项目/句子会级联清理录音**：但录音本身没有单独删除入口。

## 3. 影响

### 3.1 存储成本

- 同一句反复录 N 次 → N 个对象 + N 行记录，全部长期保留。
- 用户不会主动清理，录音会持续累积。
- 若按每分钟录音估算，长期成本不可忽略（尤其用户量大时）。

### 3.2 用户体验

- 用户可能以为“再次录音 = 覆盖”，但实际旧录音仍在后端。
- 刷新/换设备后看不到之前录音，容易误以为丢了。
- 想做“多次对比/进步曲线”时，数据库有数据但前端没入口。

### 3.3 数据一致性

- 没有唯一约束，同一句可以无限追加。
- 两个标签页/两台设备同时录同一句 → 两条记录；UI 各自显示自己的最新，DB 保留两条。
- “最新”判断依赖 `id`，不能依赖 `created_at`。

### 3.4 隐私与合规

- 录音**上传到服务端 MinIO**，不是仅本地；隐私政策需要明确说明。
- 需要决定保留期限（如 30 天）和删除权（用户删除项目/句子时清理）。
- 若未来做发音评分，录音上传是前提；当前不做评分但已上传。

### 3.5 删除与 GC

- 项目删除会清理录音对象；但如果只删 segment（没有接口）或异常中断，可能留下孤儿对象。
- 没有录音级别的 GC/对账任务。

## 5. 方案对比

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| A. 只保留最新 | 存储最省、逻辑简单、符合“覆盖”直觉 | 无法回听历史、无法做进步对比 | 轻量工具 |
| B. 保留全部 + 列表 | 可回听、可对比、数据完整 | 存储增长、需要 UI/接口 | 学习类产品 |
| C. 保留最近 N 次 | 平衡存储与体验 | 需要清理策略/任务 | 推荐折中 |

**建议**：先做 **B 的最小版**（新增列表接口 + `take_no`，前端展示“最近 3 次”），再在 P1 加保留期清理；如果产品明确“只要最新”，再切 A。

---

## 6. 验收标准

- 同一句录 3 次：DB 有 3 条记录，MinIO 有 3 个对象（当前行为）。
- 列表接口按 `id DESC` 返回，最新在前。
- 前端能显示“我的录音（第 N 次）”，可回放任意一次。
- 删除项目后，该项目的录音对象与 DB 记录都不存在。
- 若启用保留策略，超过保留期的录音被清理，且有日志/监控。
